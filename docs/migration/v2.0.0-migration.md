# v2.0.0 migration

Sequencing, cutover, and rollback for the platform migration.

Task-level detail lives in [`../../TODO.md`](../../TODO.md). This document covers the parts that
are about *order* and *risk* rather than about what to build.

## 1. Order

Seven phases. The dependencies are real — each phase blocks the next for a concrete reason.

| # | Phase | Repo | Blocked by | Because |
| --- | --- | --- | --- | --- |
| 1 | Standards | `dileepadev` | — | Nothing can implement against an unwritten design system |
| 2 | API | `api-dileepa-dev` | 1 | Both frontends read from it; projects and sessions do not exist yet |
| 3 | Main site | `dileepa-dev` | 1, 2 | Needs the design system and the new endpoints |
| 4 | Blog + redirects | `blog-dileepa-dev`, `dileepa-dev` | 3 | Cannot decommission until the blog renders elsewhere |
| 5 | Admin | `admin-dileepa-dev` | 1, 2, 3 | Follows the main site's design system |
| 6 | Links | `links-dileepa-dev` | 1, 3 | Follows the design system |
| 7 | Public build log | `dileepadev.github.io` | 1, 3 | Follows the design system; preview screenshots need the other apps rebranded |

Phase 7 has no early-landing exception: it is a dashboard, and it follows the design system
like every other frontend. Brand assets live in `dileepadev/docs/brand/` and never move.

## 2. Cutovers

Three moments where something switches over irreversibly enough to deserve a plan.

### 2.1 API: NestJS → FastAPI

**Both stacks run in parallel.** FastAPI goes up on FastAPI Cloud at its
`*.fastapicloud.dev` URL while NestJS keeps serving `api.dileepa.dev`.

1. Build FastAPI to parity, proven by contract tests written against the **current** NestJS
   responses.
2. Point a preview deployment of `dileepa-dev` and `admin-dileepa-dev` at the FastAPI URL.
3. Exercise every flow, including admin writes and the contact form.
4. Attach `api.dileepa.dev` to the FastAPI Cloud app. **Confirm custom domains are available on
   the account before this point** — see [`../architecture/platform-overview.md`](../architecture/platform-overview.md) §3.2.
5. Watch for a rollback window.
6. Only then remove `src/`, `package.json`, and the Node toolchain.

**Rollback:** repoint DNS at the Vercel deployment. Keep it deployable until the window closes.

**The risk that is not about DNS:** existing bcrypt password hashes must validate under
`passlib[bcrypt]`, and the JWT algorithm, secret handling, and claim names must match. Test
against a **real hash pulled from the database** during Phase 2, not at cutover. If they cannot
be made compatible, a forced password reset is acceptable — planned, documented in
`CHANGELOG.md`, and with a working recovery path.

### 2.2 Blog: standalone site → main site

`blog.dileepa.dev` is **retired rather than redirected**. The shared links that pointed at it
were updated at their source, so no redirect layer stands between the old host and the new one.
That decision, and what it costs, is recorded in
[`../architecture/redirects.md`](../architecture/redirects.md) §1.

This removes the ordering constraint that used to make this the most delicate part of the
migration — there is nothing that has to answer the old host, so nothing has to be stood up
before Pages is switched off:

1. All 18 posts render at `dileepa.dev/blog/{slug}` — verified.
2. Tag `blog-dileepa-dev` `v2.0.0` to archive the final Astro build.
3. Delete the Astro application and the Pages workflow. ✅
4. Disable GitHub Pages for the repository.
5. Remove the `blog.dileepa.dev` DNS record.
6. Remove the `blog.dileepa.dev` property from Search Console. **Not** a change of address —
   that tool requires 301s from the old URLs, and there are none.
7. Freeze `CHANGELOG.md`. ✅

**Step 1 still comes first.** Deleting the app before the main site actually serves the posts
would leave the content published nowhere.

**The one carry-over that is still required** is the legacy slug redirect, which lived in the
blog's `astro.config.mjs` and is easy to lose with that file. It becomes a same-site rule on
`dileepa.dev`. See `redirects.md` §2.

**Rollback:** through step 3, the Astro app is recoverable from Git history on the feature
branch. After it, only from the `v2.0.0` tag — which is why that tag exists.

Full map and verification commands: [`../architecture/redirects.md`](../architecture/redirects.md).

### 2.3 Data: blog rows and events → sessions

Both are destructive rewrites of production data.

1. Take a **verified, restore-tested** MongoDB backup. Restore-tested means restored somewhere
   and checked, not just taken.
2. Dry-run the migration; diff the output.
3. Apply. Keep the previous values under `legacy` for one release.
4. Drop `legacy` in v2.1.0.

The blog rewrite touches `link` and `bannerUrl` on 18 rows. The events migration reshapes every
event document into the sessions model.

## 3. Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Decommissioning the blog before redirects are live | Every indexed URL dies; ranking loss is slow to recover | The eight-step order in §2.2 |
| GitHub Pages cannot 301 | Meta-refresh fallback transfers ranking poorly | Move DNS to a host that can |
| FastAPI Cloud custom domain unavailable | API cannot serve `api.dileepa.dev` | Verify on the account before decommissioning Vercel |
| bcrypt hashes incompatible | Locked out of the admin | Test with a real hash in Phase 2 |
| Blog URL rewrite in MongoDB | Data loss | Verified backup, dry-run, `legacy` field |
| Hard-coded hex instead of tokens | The platform fragments again | Token import is the only sanctioned path |
| Vendored token copies drift | Two apps, two palettes | One canonical file; push changes into each consuming repo deliberately |
| Broken `dileepadev.github.io` hot-links | Silent — nothing fails | Migrate previews one project at a time; delete only after every reference is updated |
| MDX parity gap | Posts render worse than before | Port `Pre`, `SeriesBox`, `TocFab`, `Share` deliberately |
| Scope size | A stalled half-migration | Ship per phase behind `dev` previews |

## 4. What "done" means

The migration is complete when:

- [ ] All seven repositories are on `2.0.0`
- [ ] Every UI follows the design system, with tokens imported rather than re-declared
- [ ] No second accent hue anywhere; weights 400/500/700 only
- [ ] FastAPI serves `api.dileepa.dev`; NestJS is removed
- [ ] Projects and sessions exist in the API, the admin, and the main site
- [ ] The blog renders at `dileepa.dev/blog` with parity on formatting, highlighting, ToC,
      share, and read-next
- [ ] All 18 posts return a direct **200** at `dileepa.dev/blog/{slug}`, verified in production
- [ ] The legacy slug returns a single-hop 301 to a live 200
- [ ] The standalone blog is decommissioned and the blog repo is content-only
- [ ] Documentation and branding are centralised in `dileepadev`
- [ ] Lighthouse ≥ 95 on all four categories for the homepage, a blog post, and a session page

## 5. After the release

- **Keep the same-site redirects indefinitely.** There are only two rules — the legacy slug and
  `/sessions` — and the cost of keeping a redirect rule is nothing. Removing one is what costs.
- **Watch Search Console** for `dileepa.dev` coverage over the first few weeks. Expect crawl
  errors against `blog.dileepa.dev` as the old URLs drop out; that is the accepted cost of
  retiring the host rather than redirecting it, not a regression to fix.
- **Do not touch the brand guide.** It says "change at most one thing per review" — queue
  changes rather than making them.
- **Revisit the closed decisions only with a reason.** Links staying static, the API host, the
  image backend, and the content pipeline are recorded in
  [`../architecture/platform-overview.md`](../architecture/platform-overview.md) §3. Changing one
  is a platform decision, not a repo decision.
